# `engine/` (PSX runtime engine)

The engine layer that sits on top of the [SDK](../sdk): a Scene/App
framework, BSP renderer, gameplay runtime and shared data contracts. The
crates target PS1 hardware and also support host-side cooking, preview and
tests. Authored games and the editor-playtest runtime build on this layer.

`engine/Cargo.toml` is its own workspace; each example under
[`examples/`](examples) is additionally its own workspace so it can carry
PSX target flags independently.

## Crates

| Crate | Purpose |
|-------|---------|
| [`psx-engine`](crates/psx-engine) | Scene/App framework + canonical unit types (`Angle`, `Frames`) on top of the SDK. |
| [`psx-bsp`](crates/psx-bsp) | PXBSP parsing, visibility, collision and rendering. |
| [`psx-game-runtime`](crates/psx-game-runtime) | Streaming, asset residency, actors, combat, poise, projectiles and game-state systems. |
| [`psx-render-contract`](crates/psx-render-contract) | Shared rendering contracts used by the cooker and runtime. |
| [`psx-level`](crates/psx-level) | Shared `no_std` level manifest schema: assets, materials, rooms, residency. Generated by the editor, consumed by the runtime. |

## How it runs

- **Fixed 60 Hz simulation, 30 fps visual target.** The simulation advances one
  fixed tick per NTSC VBlank (a fixed timestep off the hardware vblank counter),
  while rendering targets every second vblank. Under load, visual frames drop
  without slowing the gameplay clock, so controls stay responsive.
- **Fixed-point device math and bounded memory.** Guest code uses `no_std`
  and integer/fixed-point arithmetic. Rendering uses fixed-capacity buffers and
  arenas; loading and runtime setup also use allocated storage. Memory budgets
  and the linked image matter more than a blanket claim of no allocation.
- **Cooked visibility and collision.** BSP projects use the PXBSP path; older
  grid/room projects retain their own visibility and residency paths. Their
  costs and constraints differ, so test the backend the project actually uses.
